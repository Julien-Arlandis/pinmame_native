flip-g80 — Documentation API

flip-g80 est un bundle JavaScript autoexécutable qui encapsule le moteur PinMAME (Gottlieb System 80) compilé en WebAssembly. Un seul fichier (web/flip-g80), deux consommateurs :

ConsommateurCommentRôle
web/index.html new Worker('flip-g80') Workbench navigateur — UI, afficheur, lampes, audio via Web Audio.
node/main.js require('flip-g80') Serveur Node.js — expose le moteur sur WebSocket (port 8765) + BLE peripheral.
node node/main.js --rom=bonebstr

Le bundle expose deux couches d'API distinctes, choisir selon le contexte :

  • API directe (§2) — utiliser createEmulator() dans le même process. Méthodes JS synchrones, événements typés. C'est la couche de base.
  • Protocole texte (§3-4) — client externe sur WebSocket ou BLE. Langage-agnostique. handleLine() est un désérialiseur qui appelle l'API directe en interne.

2. API directe — createEmulator()

Utilisée quand le bundle tourne dans le même process que votre code (Worker navigateur, script Node.js). createEmulator() retourne un objet avec trois familles de méthodes : abonnements, getters, setters. Le protocole texte (§3-4) est simplement un désérialiseur au-dessus de ces méthodes — il n'ajoute aucune logique propre.

Hardware réel : sur un flipper physique, les switches sont déclenchés par la bille et les mécanismes (bumpers, cibles…). C'est le HAL (ESP32 GPIO, ou votre code capteur) qui appelle setSwitch(). Les lampes et solenoids sont émis par le moteur vers votre code. Les switches vont donc dans le sens inverse des lampes/solenoids — mais tous sont exposés symétriquement via abonnements et getters.

2a. Abonnements aux événements

Plusieurs abonnés peuvent coexister sur chaque événement (tableaux internes, pas de remplacement).

MéthodeSignature du callbackDéclenché quandSens
onSwitch(id, cb) cb(state: 0|1) Le switch id change d'état (bille, bouton, capteur — appelant setSwitch()). → moteur
onSwitches(cb) cb(id: number, state: 0|1) N'importe quel switch change — version globale. → moteur
onLamps(cb) cb(lamps: Uint8Array[12]) La matrice de lampes change (émis par le moteur à chaque frame modifiée). ← moteur
onSolenoid(id, cb) cb(state: 0|1) Le solénoïde id change d'état (émis par le moteur). ← moteur
onSolenoids(cb) cb(mask: uint32) N'importe quel solénoïde change — version globale (bitmask 32 bits). ← moteur
onDisplay(cb) cb(raw: string) L'afficheur VFD est mis à jour — 160 chars hex (40 × uint16). ← moteur
onDisplayText(cb) cb(text: string) Même contenu décodé en texte ASCII (System 80B : alphanumérique ; 80/80A : 7-seg). ← moteur
Switches vs Solenoids : ce sont deux circuits hardware distincts sur un vrai flipper. Les switches (swMatrix) sont une matrice de capteurs lus par le CPU — ils vont de l'extérieur vers le moteur. Les solenoids (coreGlobals.solenoids) sont des sorties transistor directes activées par le CPU — ils vont du moteur vers l'extérieur. Les lampes (lampMatrix) sont une troisième matrice multiplexée, elle aussi émise par le moteur.

2c. Setters — écriture vers le moteur

Chaque setter écrit dans la mémoire partagée lue par le CPU WASM à la prochaine frame, et notifie immédiatement les abonnés enregistrés.

MéthodeParamètresEffet
setSwitch(id, state)id 0-79, state 0|1Écrit HEAPU8[corridor+100+id]. Notifie onSwitch / onSwitches.
setDip(id, state)id 0-31, state 0|1Écrit HEAPU8[corridor+400+id].
setSoundCmd(cmd)cmd 0-255Injecte une commande sonore directe (bypass CPU).
setAudioDistance(dist)entierDistance simulateur (mix audio).
setAudioMix(chip, dac)float, floatBalance chip/DAC.
setAudioSep(on)booleanSéparation stéréo.
setScopeActive(on)booleanActive/désactive le flux oscilloscope.
startCapture()—Démarre la capture brute des bus son.
stopCapture()—Arrête la capture.

Exemple complet — usage direct

const { createEmulator } = require('flip-g80');

const emu = createEmulator({
    sendLine(channel, line) {},          // requis mais peut être vide si on n'utilise pas le protocole texte
    sendAudio(left, right) { /* PCM */ },
    loadRom: (name) => require('fs').promises.readFile(`./roms/${name}.zip`)
});

emu.sendMessage('INIT_ENGINE', { customRomName: 'bonebstr' });

// Abonnements — déclarés avant le boot, actifs dès la première frame
emu.onSwitch(14, state => console.log(`Bumper central → ${state ? 'actif' : 'relâché'}`));
emu.onSolenoid(4, state => console.log(`Flipper gauche → ${state ? 'ON' : 'OFF'}`));
emu.onLamps(lamps => {
    // lamps : Uint8Array(12) — col × 8 lampes
    const allumee = (col, row) => (lamps[col] >> row) & 1;
});
emu.onDisplay(raw => { /* 160 chars hex */ });
emu.onDisplayText(text => console.log('Score :', text));

// Depuis un capteur physique (GPIO, tilt, bille) :
emu.setSwitch(14, 1);   // bille touche le bumper
emu.setSwitch(14, 0);   // bille repart

// Lecture synchrone à tout moment :
console.log('Flipper gauche actif :', emu.getSolenoid(4));
console.log('Lampe [col=3, row=5] :', emu.getLamp(3, 5));

3. Protocole texte — entrées (client → moteur)

Utilisé quand le client est externe (WebSocket, BLE). En interne, handleLine(line) parse ces lignes et appelle directement les setters de l'API directe (§2c) — il n'existe aucune logique supplémentaire dans cette couche.

LigneParamètresAppel interne
@set:id=<n>&state=<0|1>id 0-79setSwitch(id, state)
@dip:id=<n>&state=<0|1>id 0-31setDip(id, state)
@sound:cmd=<n>cmd 0-255setSoundCmd(cmd)
@audio:distance=<n>&chip=<f>&dac=<f>&sep=<0|1>tous optionnelssetAudioDistance / setAudioMix / setAudioSep
@scope:on=<0|1>setScopeActive(on)
@capture:action=start|stopstartCapture() / stopCapture()
@connect:input=1&display=1&driver=1(géré par le serveur Node.js, pas par handleLine) — renvoie liste ROMs + derniers états.
@reboot:(idem serveur) — recrée l'émulateur.
@rom:name=<n>&data=<base64>(idem serveur) — change la ROM puis reboot.

4. Protocole texte — sorties (moteur → client)

Émises par sendLine(channel, line) à chaque événement interne — simultanément aux callbacks de l'API directe (§2a). Un client WebSocket/BLE ne voit que ces lignes texte.

LigneParamètresÉvénement
!set:id=<n>&state=<0|1> id solénoïde 0-31 Solénoïde activé/désactivé par le CPU (émis uniquement sur changement).
!lamp:<24 hex> 12 octets en hex Matrice lampes complète (96 lampes), renvoyée en bloc à chaque frame modifiée.
!display:action=raw&data=<hex> 160 chars hex (40 × uint16) Afficheur VFD brut.
!display:action=text&data=<urlencoded> texte ASCII Afficheur décodé en texte.
@status:state=loading|ready&rom=<nom> Cycle de vie du moteur.
@machine:rom=…|cpu=…|snd=…|stereo=0|1|rate=…|dsp=80|80B Infos machine au boot. dsp=80B = 14 segments alphanumérique ; dsp=80 = 7 segments. Le client choisit son renderer en conséquence.
@sound:chips=<liste> Puces son actives.
@roms:list=<a,b,c> noms encodés URL Liste ROMs disponibles (envoyée après @connect:).
@audio:cmd=0x<hex> Log commande audio (diagnostic).

Exemple — client WebSocket minimal

const WebSocket = require('ws');
const ws = new WebSocket('ws://localhost:8765');

ws.on('open', () => ws.send('@connect:input=1&display=1&driver=1'));

ws.on('message', (data) => {
    const line = data.toString().trim();
    if (line.startsWith('!set:')) {
        const p = new URLSearchParams(line.slice(5));
        console.log(`Solénoïde ${p.get('id')} → ${p.get('state') === '1' ? 'ON' : 'OFF'}`);
    }
    if (line.startsWith('!lamp:')) {
        const hex = line.slice(6);
        // 12 octets, bit col×8+row = lampe id
    }
});

// Signaler que la bille a touché le switch n°14
ws.send('@set:id=14&state=1');

5. Canal audio

L'audio ne passe jamais par le protocole texte.

  • API directe : le callback sendAudio(left, right) passé à createEmulator() reçoit des Float32Array stéréo à 44 100 Hz à intervalle régulier.
  • Serveur Node.js : l'audio est envoyé au haut-parleur local (SoX/ALSA). Il n'est pas transmis sur le WebSocket ni le BLE — un client réseau ne reçoit pas l'audio.
  • Worker navigateur : forwarde via postMessage({ channel: 'audio', left, right }).
  • ESP32 natif : streamé sur BLE avec flag 0x02 (vs 0x00/0x01 pour le texte). Format : PCM mono unsigned 8-bit à 11 025 Hz (sous-échantillonnage ×4). Le client navigateur (ble-central.js) joue les échantillons via un AudioContext dédié.
CanalActivationPayloadUsage
capturestartCapture() / @capture:action=start{ ym_L, ym_R, dac } Float32ArrayEnregistrement brut des bus son.
scopesetScopeActive(true) / @scope:on=1{ ym_L, ym_R, dac, spk_L, spk_R }Oscilloscope temps réel.

6. Serveur Node.js

node node/main.js --rom=bonebstr

Démarre un serveur WebSocket sur ws://localhost:8765 (configurable via --port=) et un périphérique BLE (service ab120001-…), sauf --no-ble.

À la connexion d'un client, le serveur envoie :

@master:name=runtime-node&version=1

Si le client répond @connect:input=1&display=1&driver=1, le serveur renvoie la liste des ROMs et les derniers états connus (display, lampes, statut) pour que le client rattrape l'état courant.

7. Annexe — web/interface.js (client navigateur du repo)

SerialMaster n'est utile que pour le workbench de ce repo. Si vous écrivez votre propre client (Python, microcontrôleur, autre navigateur…), ignorez cette section et utilisez directement l'API directe (§2) ou le protocole texte sur WebSocket/BLE (§3-4).

Enveloppe un transport (Worker / WebSocket / BLE) derrière une API unique orientée lignes texte — c'est la couche utilisée par web/index.html pour unifier ses trois modes de connexion.
