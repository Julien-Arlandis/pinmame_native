tilt_node / tilt_web — Documentation du protocole

node/bundle.js assemble le même moteur (node/runtime.js + node/runtime-audio.js + WASM PinMAME) en deux bundles indépendants :

BundlePour quiCe qu'il contient
node/tilt_node Émuler un flipper en standalone. C'est le seul fichier nécessaire. Exécutable Node.js autonome : moteur PinMAME + serveur WebSocket (port 8765) + périphérique BLE intégrés. node node/tilt_node --rom=... et c'est tout — aucun navigateur, aucun autre fichier du repo requis.
web/tilt_web Servir le moteur à un navigateur (le workbench de ce repo). Le même moteur, packagé pour tourner en Web Worker côté client. web/interface.js + web/index.html s'en servent pour le mode "Local" du workbench — c'est un cas d'usage parmi d'autres, pas une dépendance du protocole.

Le protocole texte est strictement le même dans les deux cas — c'est lui, et non un fichier JS particulier, qui constitue l'API. Si vous pilotez un flipper avec tilt_node, vous n'avez besoin que des sections 1 à 4 ci-dessous (lignes entrantes/sortantes, audio) appliquées par-dessus une connexion WebSocket ou BLE — dans n'importe quel langage. web/interface.js (§6, en annexe) n'est qu'un client parmi d'autres possibles, celui du workbench navigateur fourni avec le repo ; il ne fait pas partie du pack tilt_node et n'est requis pour rien d'autre que cette UI-là.

1. Émuler un flipper avec tilt_node seul

node node/tilt_node --rom=bonebstr
# ou, sans bundle pré-généré : node node/main.js --rom=bonebstr

Ça suffit. tilt_node démarre :

  • un serveur WebSocket sur ws://localhost:8765 (port configurable via --port=) ;
  • un périphérique BLE annoncé sous le nom tilt_node (service ab120001-…), sauf --no-ble ;
  • la sortie audio directement sur le haut-parleur de la machine (SoX/ALSA), sauf --no-speaker.

N'importe quel client — navigateur, script Python, microcontrôleur — peut alors s'y connecter en WebSocket ou BLE et échanger les lignes de protocole des §2-3 ci-dessous. Le client n'a pas besoin de connaître createEmulator ni aucun fichier JS du repo : il parle juste ce protocole texte sur le socket.

Au moment de la connexion, tilt_node envoie immédiatement :

@master:name=runtime-node&version=1

puis, si le client envoie @connect:input=1&display=1&driver=1, il renvoie la liste des ROMs disponibles et les derniers états connus (affichage, lampes, statut) — pratique pour qu'un client qui se connecte en cours de partie rattrape l'état courant sans attendre le prochain changement.

createEmulator({ sendLine, sendAudio, sendCapture, sendScope, loadRom }) (dans node/runtime.js) est le moteur interne que tilt_node appelle pour faire tourner le WASM PinMAME et router les lignes. Vous n'avez besoin d'y toucher que si vous embarquez le moteur comme librairie dans votre propre process Node (comme le fait node/main.js) — pas pour piloter un flipper via WebSocket/BLE, ce qui est le cas d'usage normal.

2. Lignes entrantes — client → émulateur (@…)

Écrites par le client directement sur le WebSocket ou la caractéristique BLE IN de tilt_node (une ligne = un message). En interne, tilt_node les transmet à emulator.handleLine(line).

LigneParamètresEffet
@set:id=<n>&state=<0|1>id = n° switch (0-79), stateChangement d'état d'un switch/contact — écrit l'octet dans la mémoire WASM lue par le jeu.
@dip:id=<n>&state=<0|1>id = n° dip-switchChange un dip-switch.
@sound:cmd=<n>cmd = commande son (0-255)Injecte une commande sonore directement (bypass CPU).
@audio:distance=<n>&chip=<f>&dac=<f>&sep=<0|1>tous optionnelsRéglages mix audio (distance simulateur, balance chip/DAC, séparation stéréo).
@scope:on=<0|1>Active/désactive l'envoi du canal scope.
@capture:action=start|stopDémarre/arrête la capture brute des bus son.
@connect:input=1&display=1&driver=1(géré côté tilt_node, pas par handleLine)Annonce de connexion d'un client ; déclenche le renvoi de la liste de ROMs + derniers états connus.
@reboot:(idem, côté tilt_node)Recrée intégralement l'émulateur (reboot dur).
@rom:name=<n>&data=<base64>(idem, côté tilt_node)Change/injecte une ROM puis reboot.

3. Lignes sortantes — émulateur → client (!… / @…)

Reçues telles quelles sur le WebSocket ou en notification BLE depuis tilt_node (une ligne par message).

LigneParamètresÉvénement représenté
!set:id=<n>&state=<0|1> id = n° solénoïde/transistor (0-31) Changement de sortie transistor / solénoïde. Émise uniquement sur changement d'état (32 bits comparés à l'état précédent).
!lamp:<24 car. hex> 12 octets (colonnes) × 8 lampes État complet de la matrice de lampes (96 lampes), renvoyé en bloc à chaque frame modifiée.
!display:action=raw&data=<hex> 40 caractères VFD encodés en hex (16 bits/caractère) Contenu brut de l'afficheur.
!display:action=text&data=<urlencoded> texte ASCII Contenu de l'afficheur en texte (utilisé notamment pour la sortie série display).
@status:state=loading|ready&rom=<nom> Cycle de vie du moteur (chargement / ROM prête).
@machine:cpu=…|snd=…|stereo=0|1|rate=… Infos machine détectées (CPU, puces son, stéréo, fréquence).
@sound:chips=<liste> Liste des puces son actives (compatibilité Node).
@roms:list=<a,b,c> noms encodés URL, séparés par virgule Liste des ROMs disponibles côté serveur (tilt_node).
@audio:cmd=0x<hex> Log d'une commande audio reçue par le moteur son (diagnostic).

4. Canal audio (binaire, séparé du texte)

L'audio ne passe jamais par les lignes texte : c'est un canal dédié pour éviter la latence/charge du parsing. Le moteur appelle sendAudio(left, right) à intervalle régulier (pacing géré par node/runtime-audio.js / audio.startPacing()).

  • tilt_node (standalone) : l'audio est converti en PCM 16-bit stéréo (floatTo16BitPCM) et écrit directement dans le sink choisi sur la machine qui exécute tilt_node — haut-parleur via play/SoX (macOS) ou aplay/ALSA (Linux), ou fichier avec --audio-out=. Il n'est jamais envoyé sur le WebSocket ni le BLE — un client réseau ne reçoit pas l'audio, seulement les lignes texte des §2-3.
  • Worker (navigateur, tilt_web) : seul ce mode forwarde l'audio au code JS appelant via worker.postMessage({ channel: 'audio', left, right }) → port.onAudio(cb), parce que le Worker tourne dans le même process que la page qui doit le jouer.

5. Canaux capture / scope

CanalActivationPayloadUsage
capture@capture:action=start{ ym_L, ym_R, dac } (Float32Array)Enregistrement brut des bus son (debug/diagnostic).
scope@scope:on=1{ ym_L, ym_R, dac, spk_L, spk_R }Oscilloscope temps réel affiché dans l'interface (bouton scopeBtn).

6. Annexe — web/interface.js (client navigateur du repo, optionnel)

Cette section ne concerne que le workbench navigateur fourni dans ce repo (web/index.html + web/interface.js). Si vous écrivez votre propre client pour piloter un flipper via tilt_node (en JS, Python, sur microcontrôleur…), vous n'avez pas besoin de cette classe : parlez directement le protocole texte des §2-3 sur le WebSocket/BLE. SerialMaster n'est qu'une enveloppe pratique utilisée par l'UI de ce repo pour unifier ses trois transports (Worker local, WebSocket, BLE) derrière une seule API JS.

Classe définie dans web/interface.js. Enveloppe un transport (Worker / WebSocket / BLE) derrière une API unique — c'est l'objet que manipule le reste de l'interface (master.send(...), etc.).

MéthodeSignatureRôle
sendsend(line: string)Envoie une ligne @… vers l'émulateur (switch, dip, etc.).
onMessageonMessage(cb: (line: string) => void)S'abonne à toutes les lignes texte sortantes (!set:, !lamp:, !display:, @status:, …). Plusieurs abonnés possibles (liste interne).
onAudioonAudio(cb: (left: Float32Array, right: Float32Array) => void)S'abonne au flux audio PCM flottant.
onCaptureonCapture(cb: (d) => void)S'abonne au canal de capture brute.
onScopeonScope(cb: (d) => void)S'abonne au flux oscilloscope.
onDisconnectonDisconnect(cb: () => void)Appelé à la fermeture du transport.
namegetterNom du maître connecté.

7. Recettes — brancher une fonction sur un événement

Client minimal — WebSocket pur, sans interface.js ni navigateur

Exemple Node.js (module ws) qui se connecte à tilt_node et réagit aux sorties transistor :

const WebSocket = require('ws');
const ws = new WebSocket('ws://localhost:8765');

ws.on('open', () => ws.send('@connect:input=1&display=1&driver=1'));

ws.on('message', (data) => {
    const line = data.toString().trim();
    if (line.startsWith('!set:')) {
        const p = new URLSearchParams(line.slice(5));
        console.log(`Solénoïde ${p.get('id')} → ${p.get('state') === '1' ? 'ON' : 'OFF'}`);
    }
});

// Simuler l'appui sur le switch n°27 (pièce)
ws.send('@set:id=27&state=1');
Les recettes suivantes utilisent master.send(...) / master.onMessage(...), l'objet SerialMaster du workbench (§6) — purement pour la concision. Avec un client maison, c'est exactement ws.send(line) / ws.on('message', cb) comme dans la recette ci-dessus.

Détecter un changement de switch (entrée)

Les switches sont des entrées envoyées par l'hôte vers l'émulateur — il n'y a pas d'« événement switch » émis par le moteur ; c'est vous qui le déclenchez (bouton UI, capteur physique, etc.).
// Faire passer le switch n°27 (pièce) à l'état "actif"
master.send('@set:id=27&state=1');
// ... puis relâché
master.send('@set:id=27&state=0');

Écouter les sorties transistor / solénoïde

master.onMessage((line) => {
    if (!line.startsWith('!set:')) return;
    const p = new URLSearchParams(line.slice(5));
    const id    = parseInt(p.get('id'));    // 0-31
    const state = parseInt(p.get('state')); // 0 ou 1
    console.log(`Solénoïde ${id} → ${state ? 'ON' : 'OFF'}`);
});

Écouter les lampes

master.onMessage((line) => {
    if (!line.startsWith('!lamp:')) return;
    const hex = line.slice(6);
    for (let col = 0; col < 12; col++) {
        const mask = parseInt(hex.slice(col * 2, col * 2 + 2), 16);
        for (let row = 0; row < 8; row++) {
            const lampId = col * 8 + row;
            const state  = (mask >> row) & 1;
            // ... réagir au changement
        }
    }
});

Écouter l'affichage (VFD)

master.onMessage((line) => {
    if (line.startsWith('!display:action=text&data=')) {
        const text = decodeURIComponent(line.slice(26));
        console.log('Affichage :', text);
    }
});

Récupérer la sortie audio (mode Worker navigateur uniquement)

Ne s'applique pas à un client WebSocket/BLE de tilt_node : voir §4, l'audio y reste local à la machine qui exécute tilt_node.
master.onAudio((left, right) => {
    // left/right : Float32Array, 44100 Hz, valeurs [-1, 1]
    monAudioContext_feed(left, right);
});

Suivre le cycle de vie du moteur

master.onMessage((line) => {
    if (!line.startsWith('@status:')) return;
    const state = new URLSearchParams(line.slice(8)).get('state');
    if (state === 'ready') console.log('Moteur prêt');
});

Côté Node.js — utiliser createEmulator directement

const { createEmulator } = require('./tilt_web');

const emulator = createEmulator({
    sendLine(channel, line) {
        if (line.startsWith('!set:'))   { /* sortie transistor */ }
        if (line.startsWith('!lamp:'))  { /* lampes */ }
        if (line.startsWith('@status:')) { /* cycle de vie */ }
    },
    sendAudio(left, right) { /* PCM flottant 44100 Hz */ },
    loadRom: (name) => require('fs').promises.readFile(`./roms/${name}.zip`)
});

emulator.sendMessage('INIT_ENGINE', { customRomName: 'bonebstr' });

// Simuler un appui sur un switch
emulator.handleLine('@set:id=27&state=1');

Référence du protocole texte : commentaire en tête de web/interface.js ; implémentation moteur : node/runtime.js (fonction createEmulator + handleLine) ; audio : node/runtime-audio.js ; assemblage du bundle : node/bundle.js.
